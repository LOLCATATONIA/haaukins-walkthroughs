WireGuard-VPN på Linux: fuld opsætning og fejlsøgning

Den fulde WireGuard-gennemgang: installation, verificering af forbindelsen, og fejlsøgning når noget ikke virker.

ForudsætningHaaukins CTF

1. Installér WireGuard

Installér via din distributions pakkehåndtering:

# Arch Linux / CachyOS
sudo pacman -S wireguard-tools

# Debian / Ubuntu
sudo apt install wireguard

# Fedora
sudo dnf install wireguard-tools

For andre distributioner, se WireGuards egen installationsside. Du skal normalt ikke installere resolvconf manuelt. Det er kun relevant hvis konfigurationen bruger en DNS =-indstilling, hvilket Haaukins-konfigurationer typisk ikke gør.

2. Download og installér din konfiguration

Download .conf-filen fra Haaukins' event-side. Den ligner noget i stil med:

[Interface]
Address = 25.17.240.251/32
PrivateKey = ...
MTU = 1420

[Peer]
PublicKey = ...
AllowedIPs = 77.205.40.0/24,25.17.240.1/32
Endpoint = special.sec04.haaukins.dk:5385
PersistentKeepalive = 25
⚠️ Brug altid den aktuelle konfiguration. VPN-konfigurationer er ikke permanente. En ny fil kan have en anden adresse, privat nøgle og lab-subnet, selvom endpoint og serverens public key er uændret. Et team har typisk én konfigurationsfil pr. medlem; del aldrig din private nøgle med andre.

Kopiér filen til /etc/wireguard/ og begræns rettighederne, så kun root kan læse den private nøgle:

sudo install -m 600 ./<navn>.conf /etc/wireguard/

Et alternativ er at køre wg-quick up direkte på filens sti uden at kopiere den først (det virker også, se trin 3), men at samle konfigurationerne i /etc/wireguard/ holder dem ét sted med korrekte rettigheder.

3. Forbind

sudo wg-quick up <navn>      # uden .conf, fx: sudo wg-quick up wg-conf-1
⚠️ Faldgrube: interfacenavnet må højst være 15 tegn. wg-quick bruger filnavnet som Linux-netværksinterfacets navn, og kernen tillader kun 15 tegn (IFNAMSIZ). Hedder din fil fx wg-conf-1-hardcore.conf (19 tegn), fejler kommandoen med "must be a valid interface name". Kopiér filen til et kortere navn og brug det i stedet: cp wg-conf-1-hardcore.conf wg-hardcore.conf.

4. Verificér forbindelsen

sudo wg show <navn>    # eller bare: sudo wg show

Kig efter en nylig latest handshake. Tjek derefter routing:

ip route

Ved en normal split-tunnel-opsætning er kun lab-netværket routet gennem WireGuard, mens din almindelige internettrafik stadig går via din egen forbindelse. Eksempel:

default via 192.168.20.1 dev wlan0
77.205.40.0/24 dev wg-conf-1

Test routing til en konkret lab-IP:

ip route get 77.205.40.73
# forventet: 77.205.40.73 dev wg-conf-1 src 25.17.240.251
ip route get 1.1.1.1
# forventet: fortsat via din egen forbindelse, IKKE wg-interfacet

Split tunnel vs. full tunnel

Rør aldrig AllowedIPs i den udleverede konfiguration, medmindre du ved hvorfor. Særligt bør du aldrig erstatte den med:

AllowedIPs = 0.0.0.0/0

Haaukins' egen konfiguration angiver normalt kun lab-subnettet i AllowedIPs, hvilket giver split tunneling: kun lab-trafik går gennem WireGuard. 0.0.0.0/0 laver i stedet en full tunnel, hvor al din IPv4-trafik (browser, Teams, alt) pludselig sendes gennem Haaukins-VPN'en.

5. Find og brug Hosts-oplysningerne

Haaukins viser en Hosts / DNS Records-sektion på event-siden, når du starter en opgave: hostname og IP for de aktive challenge-hosts. Disse records tilføjes dynamisk, så tjek sektionen igen hver gang du starter en ny opgave eller skifter lab.

sudoedit /etc/hosts
# tilføj: 77.205.40.73 sanity-plus.hkn

Bekræft opslaget:

getent hosts sanity-plus.hkn
curl http://sanity-plus.hkn/

6. Test targetet

Start med routing, ikke ping:

ip route get <lab-ip>

Virker routingen, så test grundlæggende forbindelse:

ping -c 3 <lab-ip>

Svarer targetet ikke på ICMP, betyder det ikke nødvendigvis at det er utilgængeligt. Ping kan være blokeret selvom en service kører fint. Test derfor servicen selv, fx:

curl -v http://<hostname>/
nmap -Pn <lab-ip>   # -Pn springer host discovery over

Fejlsøgning: den forvirrende klassiker (stale /etc/hosts)

Dette er den hyppigste fælde, og den ligner at VPN'en er i stykker, selvom den ikke er det.

Symptom: ping til den aktuelle lab-IP virker fint (0% tab), men curl http://<hostname>/ eller browseren timeouter.

Årsag: når du Stop/Reset'er eller genstarter en opgave, tildeler Haaukins typisk en ny IP, synlig på Hosts-siden. Din /etc/hosts peger stadig på den gamle. Den gamle IP ligger ofte i et helt andet subnet end dit nuværende lab-subnet, så den dækkes ikke af AllowedIPs, routes ikke gennem WireGuard, og sendes i stedet ud ad din normale forbindelse hvor den rammer intet.

Diagnose:

getent hosts <hostname>         # fx 77.101.126.31 (gammelt subnet?)
ip route get 77.101.126.31      # peger den på wlan0/default i stedet for wg-interfacet?

Viser opslaget en IP uden for dit nuværende lab-subnet, og ip route get viser din normale forbindelse i stedet for WireGuard, er det netop denne fælde:

77.101.126.31 via 192.168.1.1 dev wlan0   # forkert: går ud ad normal internet

Fix: opdatér entryen til den aktuelle IP, enten manuelt eller som en hurtig erstatning:

sudo sed -i 's#^.*<hostname>.*$#<aktuel-ip> <hostname>#' /etc/hosts
getent hosts <hostname>         # skal nu vise den aktuelle IP
ip route get <aktuel-ip>        # skal nu vise dev wg-...
💡 Vane der sparer timer: hver gang du har Stop/Reset'et eller genstartet en opgave, så re-synk /etc/hosts fra Hosts-siden, før du arbejder videre. IP'en ændrer sig, og der er ingen dynamisk DNS til at fange det. Haaukins-modellen er manuel /etc/hosts.

Og husk hvad en lykkedes ping faktisk beviser: kun ICMP og routing til dén konkrete IP. Det beviser hverken at et hostname peger på den rigtige IP, eller at selve servicen svarer. Verificér altid på det niveau opgaven faktisk bruger:

getent hosts <hostname>         # resolver navnet korrekt?
ip route get <ip>               # routes det via WireGuard?
curl -v http://<hostname>/       # svarer selve servicen?

Anden fejlsøgning

Ingen handshake (sudo wg show viser ingen latest handshake): tjek ip addr og ip route, og bekræft at du rent faktisk bruger den aktuelle konfiguration fra event-siden, ikke en gammel.

Internet eller andre apps stopper med at virke: tjek ip route get 1.1.1.1. Går den gennem WireGuard-interfacet i stedet for din normale forbindelse, kig på AllowedIPs i konfigurationen (se split tunnel-afsnittet ovenfor).

Skiftet lab og intet virker længere: download den aktuelle konfiguration, genstart forbindelsen, og opdatér /etc/hosts til det nye subnet.

Hurtig reference

# Installér konfigurationen
sudo install -m 600 ./<navn>.conf /etc/wireguard/

# Forbind / afbryd
sudo wg-quick up <navn>
sudo wg-quick down <navn>

# Status og routing
sudo wg show
ip route
ip route get <lab-ip>
ip route get 1.1.1.1              # skal IKKE gå via wg-interfacet

Sikkerhed

Konfigurationsfilen indeholder en privat nøgle der autentificerer dig mod Haaukins. Del aldrig PrivateKey = ...-linjen, og behandl hele filen som følsom information. Bliver din private nøgle eksponeret, så hent en ny konfiguration fra Haaukins i stedet for at fortsætte med den kompromitterede.

Hvad du har lært

  • Installér konfigurationen i /etc/wireguard/ med install -m 600, så kun root kan læse din private nøgle.
  • Rør aldrig AllowedIPs, og især ikke til 0.0.0.0/0. Det laver en full tunnel og kan tage al din anden trafik med.
  • Den hyppigste fejl er ikke VPN'en: det er en stale /etc/hosts-entry fra før sidste lab-genstart. Re-synk den hver gang du Stop/Reset'er.
  • En lykkedes ping beviser kun ICMP og routing, ikke at hostname eller service er korrekte. Verificér på servicens eget niveau.
